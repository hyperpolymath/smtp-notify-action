= Migrating from dawidd6/action-send-mail
:toc: macro
:toclevels: 2

This action is a *migration target*, not a drop-in replacement. Nine input names
match `dawidd6/action-send-mail` exactly; fifteen are absent; and several shared
names differ in default or in meaning. Read the drift section before switching a
working workflow.

NOTE: This guide describes *v0.3.0*. The `secure` input changed behaviour in
v0.2.0: v0.1.0 treated any unrecognised value as plaintext, v0.2.0 rejects it.
v0.3.0 adds the STARTTLS submission-port route described below. Pin `@v0.3.0`,
not `@v0.1.0`, or the behaviour described
below will not be the behaviour you get.

toc::[]

== Read this first: `secure` means something different here

`secure` does not mean the same thing in both actions, and the difference is
one of behaviour rather than of naming.

[cols="1,2,2"]
|===
|`secure` |dawidd6/action-send-mail |smtp-notify-action

|`true`
|Implicit TLS from the first byte (SMTPS, normally port 465).
|Same. Implicit TLS from the first byte.

|`false`
|Plain connection that is *upgraded via STARTTLS* when the server offers it.
This is the normal path for port 587 submission.
|Same *when the server offers it* (RFC 3207). The difference is what happens
when it does not: dawidd6 carries on in the clear, this action fails the step.
It never falls back to plaintext.
|===

The input is fail-closed. It accepts exactly five values — `true` and
`implicit` for implicit TLS, `false` and `starttls` for STARTTLS, and
`plaintext` for no TLS at all — and rejects anything else outright. A typo such
as `1`, `yes`, `TRUE` or `on` fails the step rather than quietly selecting a
transport.

This is a deliberate divergence from dawidd6, where `false` means "STARTTLS
when the server offers it, and plaintext when it does not". Here the second
half is an error, not a downgrade. The reason for the strictness is
historical: v0.1.0 treated *any* unrecognised value as
plaintext, so a typo could put the username and password on the wire
base64-encoded in a session with no encryption. That was
https://github.com/hyperpolymath/smtp-notify-action/issues/1[issue #1] and it
is fixed in v0.2.0. `plaintext` survives as an explicit opt-in, intended only
for a containerized test sink.

The migration rule follows from that:

* If your dawidd6 step used `secure: true` on port 465, it ports across unchanged.
* If it used `secure: false` on port 587, it ports across too — STARTTLS has
  landed: it ships in v0.3.0.
  The one behavioural difference is a server that does not advertise
  `STARTTLS` — dawidd6 would send in the clear, this action stops. Do not
  reach for `plaintext` if that happens; check the port first.

== Read this second: Microsoft 365 works on port 587, not 465

If your dawidd6 step sends through `smtp.office365.com`, one thing changes and
one thing does not: you must be on port 587 with `secure: starttls`, and port
465 will never work.

Probed 2026-09-02, re-probed live on 2026-09-09:

* `smtp.office365.com:587` advertises exactly `AUTH LOGIN XOAUTH2`. It does not
  offer `AUTH PLAIN`.
* `smtp.office365.com:465` has no listener at all, so the implicit-TLS path
  cannot connect and no setting works around that.

All three pieces ship in v0.3.0: STARTTLS on 587, EHLO
capability parsing
(https://github.com/hyperpolymath/smtp-notify-action/issues/9[issue #9]) and
mechanism selection including `AUTH LOGIN`
(https://github.com/hyperpolymath/smtp-notify-action/issues/10[issue #10]).
The action reads the advertised list and picks `LOGIN` where `PLAIN` is absent,
so Microsoft 365 is a supported provider from the next release rather than a
documented blocker. A live handshake against `smtp.office365.com:587` was run
on 2026-09-09; authentication itself is exercised by tests rather than against
a live tenant, because no Microsoft 365 credential exists at any tier here.

`XOAUTH2` remains unimplemented and is not planned: it needs a token from an
OAuth flow, which a repository secret cannot supply. If your tenant has
disabled basic authentication for SMTP, no password-based client can send for
it — that is a tenant policy, not a gap in this action.

Google Workspace is unaffected. `smtp.gmail.com` offers `AUTH PLAIN` on both
587 and 465, with 465 accepting implicit TLS, so a Gmail-based dawidd6 step
already on port 465 ports across today; port 587 was verified live on
2026-09-09 too. Other providers were not probed: check yours with
`openssl s_client -connect host:465` before switching.

== Inputs that transfer unchanged

These nine names are identical in both actions.

`server_address` · `server_port` · `secure` · `username` · `password` ·
`from` · `to` · `subject` · `body`

== Drift inside those nine names

[cols="1,2,2"]
|===
|Input |dawidd6 |Here

|`server_port`
|Defaults to `25`.
|Defaults to `465`. If you relied on the default, you were talking to a
different port.

|`body`
|Accepts a `file://` URL to read the body from a file.
|Literal text only. A `file://` string is sent as the body text.

|`to`
|Documented as "separated with comma". Any other separator is undocumented
behaviour of the underlying mail library.
|Splits on comma, space and tab — *not* newline. A multi-line `to:` fails closed
with a header-injection error rather than mailing a mangled address, so you will
see it immediately.

|`subject`, `from`
|Declared `required: true`, which GitHub Actions does not enforce at runtime,
so an empty value reaches the step.
|Fatal if empty. The step fails rather than sending a headerless message.

|(authentication)
|Optional. Omitting `username`/`password` attempts unauthenticated relay.
|Mandatory. AUTH is a required row in the protocol state machine, so
unauthenticated relay is impossible even against a server that would allow it.
|===

== Inputs that do not exist here

`connection_url` · `html_body` · `cc` · `bcc` · `reply_to` · `in_reply_to` ·
`ignore_cert` · `convert_markdown` · `attachments` · `priority` · `headers` ·
`nodemailerlog` · `nodemailerdebug` · `envelope_from` · `envelope_to`

`cc`, `bcc`, `reply_to` and `headers` are planned
(https://github.com/hyperpolymath/smtp-notify-action/issues/5[issue #5]).

`ignore_cert` is *deliberately* absent and will not be added. Certificate
verification is always on and cannot be disabled by any input. This is the one
place where parity with dawidd6 would be a regression.

Neither action declares an `outputs:` block, so this is parity rather than a
regression: in both, failure is signalled by a non-zero exit that fails the job.

== Input that is new here

[cols="1,3"]
|===
|`handshake_only` |`true` connects, completes the TLS handshake, sends `EHLO`
and `QUIT` without sending mail. Use it to prove reachability and TLS
configuration from a runner without delivering a test message.
|===

== Runner support

*Linux x86_64 and Linux arm64 only.*

Every other runner fails with a message naming the cause. The installer gates
on operating system before architecture, because Windows and Intel macOS both
report `x86_64` from `uname -m`: an architecture-only gate downloaded the Linux
binary, passed the SHA-256 check (the file was intact — it was simply the wrong
file), and died at `exec` with an exec-format error that named nothing useful.
That was https://github.com/hyperpolymath/smtp-notify-action/issues/2[issue #2],
fixed in v0.2.0; such a runner now stops at the OS gate saying so.

If your notify job runs on `windows-latest` or `macos-13`, stay on dawidd6: the
failure is now legible, but it is still a failure.

== Worked example

.Before
[source,yaml]
----
- uses: dawidd6/action-send-mail@v3
  with:
    server_address: smtp.example.org
    server_port: 465
    secure: true
    username: ${{ secrets.SMTP_USERNAME }}
    password: ${{ secrets.SMTP_PASSWORD }}
    from: GitHub Push <ci@example.org>
    to: you@example.org,teammate@example.org
    subject: Push to ${{ github.repository }}
    body: ${{ github.actor }} pushed ${{ github.sha }}
----

.After
[source,yaml]
----
- uses: hyperpolymath/smtp-notify-action@v0.3.0
  with:
    server_address: smtp.example.org
    server_port: 465
    secure: true
    username: ${{ secrets.SMTP_USERNAME }}
    password: ${{ secrets.SMTP_PASSWORD }}
    from: GitHub Push <ci@example.org>
    to: you@example.org,teammate@example.org
    subject: Push to ${{ github.repository }}
    body: ${{ github.actor }} pushed ${{ github.sha }}
----

Only the `uses:` line changes, because this example was already inside the
nine-input subset and already on implicit TLS.

== What you gain

* *No Node runtime.* One static musl binary with `.dependencies = .{}` — zero
  third-party dependencies, so no transitive advisory surface.
* *The binary is SHA-256 pinned inside `action.yml`*, verified on every run.
* *The SMTP session is specified in Idris2 and machine-checked.* Be precise
  about what that means: the protocol state machine is a table proved
  deterministic, terminating and correctly ordered, and dot-stuffing carries a
  universally-quantified safety theorem. Header-value validation is covered by
  golden vectors, not yet by a theorem, so an injection vector outside the
  corpus is not excluded by proof; the exact boundary of the claim is set out
  in link:KNOWN-DEFECTS.adoc[`KNOWN-DEFECTS.adoc`]. The Idris2 layer is a
  specification and code generator; it does not ship in the binary.
* *Plain text only*, by construction. No HTML, no remote images, no tracking
  pixel, and clean in a screen reader.
* *Fails loudly.* No `continue-on-error`, no `|| true`, no `set +e` anywhere in
  the action.

== What you give up

HTML bodies · attachments ·
cc/bcc/reply-to · custom headers · non-Linux runners · the ability to skip
certificate verification · a large user base to search for answers in.

There is also no retry or backoff at the SMTP layer. A transient `4xx` from the
server fails the step immediately rather than being retried.

The reply text itself is not given up. Since v0.2.0 the failure message carries
the server's own words along with the code and the protocol step that produced
it, so a `535`, a `550` and a `554` are distinguishable in the log
(https://github.com/hyperpolymath/smtp-notify-action/issues/3[issue #3]). Only
bytes the server sent are echoed; no credential passes through that path.
