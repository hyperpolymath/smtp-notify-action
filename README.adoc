= smtp-notify-action
:toc: macro
:source-highlighter: rouge

Send a plain-text notification email from a GitHub workflow over TLS, by either
route: implicit TLS from the first byte (SMTPS, port 465), or a cleartext start
on the submission port that is upgraded in place with STARTTLS (RFC 3207, port
587) — which is the route Google Workspace and Microsoft 365 expect, and the
only one Microsoft 365 offers at all. **Node-free**: the action is a composite
step that runs one static binary — no `node_modules`, no container, no runtime
dependency graph.

The SMTP client session is **formally specified in Idris2** (state machine,
reply-code classes, dot-stuffing, header-injection rejection — with
machine-checked proofs) and **built in Zig** (0.16.0, static musl,
byte-reproducible). The generated state table in the binary is diffed against
the proven specification by CI on every push.

Coming from `dawidd6/action-send-mail`? Read
link:MIGRATION.adoc[`MIGRATION.adoc`] first: nine input names match exactly,
fifteen are absent, and `secure` differs in meaning.

== Usage

[source,yaml]
----
- name: Notify by mail
  uses: hyperpolymath/smtp-notify-action@<pinned-sha> # v0.4.0
  with:
    server_address: ${{ secrets.SMTP_HOST }}
    server_port: 465
    secure: true
    username: ${{ secrets.SMTP_USERNAME }}
    password: ${{ secrets.SMTP_PASSWORD }}
    from: 'GitHub Push <${{ secrets.SMTP_USERNAME }}>'
    to: 'you@example.org teammate@example.org'
    subject: 'Push to ${{ github.repository }}'
    body: '${{ github.actor }} pushed ${{ github.sha }}'
----

On the submission port, set `secure` to `starttls` and the port to 587:

[source,yaml]
----
- name: Notify by mail
  uses: hyperpolymath/smtp-notify-action@<pinned-sha> # v0.4.0
  with:
    server_address: smtp.office365.com   # or smtp.gmail.com
    server_port: 587
    secure: starttls
    username: ${{ secrets.SMTP_USERNAME }}
    password: ${{ secrets.SMTP_PASSWORD }}
    from: 'GitHub Push <${{ secrets.SMTP_USERNAME }}>'
    to: 'you@example.org'
    subject: 'Push to ${{ github.repository }}'
    body: '${{ github.actor }} pushed ${{ github.sha }}'
----

IMPORTANT: What has been verified against live servers is the *upgrade itself* —
smtp.gmail.com:587 and smtp.office365.com:587 both complete the STARTTLS
handshake and the mandatory second EHLO. Authentication on that route is covered
by tests rather than by a live send; see
link:KNOWN-DEFECTS.adoc[`KNOWN-DEFECTS.adoc`] D-005 to D-007.

These nine input names match `dawidd6/action-send-mail` exactly:
`server_address`, `server_port`, `secure`, `username`, `password`, `from`,
`to`, `subject`, `body`.

Fifteen dawidd6 inputs are *not* implemented: `html_body`, `cc`, `bcc`,
`reply_to`, `attachments`, `headers`, `priority`, `connection_url`,
`in_reply_to`, `ignore_cert`, `convert_markdown`, `envelope_from`,
`envelope_to`, `nodemailerlog`, `nodemailerdebug`. Defaults differ too:
`server_port` is `465` here rather than `25`, and `body` takes literal text
only (no `file://`). Treat this as a migration target, not a drop-in
replacement, and read the input table below before switching.

NOTE: `ignore_cert` is absent deliberately. Certificate verification is always
on and cannot be turned off by any input.

== Inputs

[cols="1,1,3"]
|===
|Input |Default |Meaning

|`server_address` |_required_ |SMTP server host name.
|`server_port` |`465` |SMTP server port.
|`secure` |`true` |Fail-closed transport selection, five accepted values.
`true` or `implicit` = implicit TLS from the first byte (SMTPS).
`false` or `starttls` = start in the clear and upgrade with STARTTLS
(RFC 3207, normally port 587). The upgrade is *mandatory*: a server that does
not advertise `STARTTLS` fails the step, because the alternative to upgrading
is to stop, not to carry on in the clear.
`plaintext` = no TLS, intended only for containerized test sinks. Any other
value is rejected outright.
|`username` |— |SMTP username. The mechanism (`PLAIN` or `LOGIN`) is chosen
from what the server advertises.
|`password` |— |SMTP password. Passed to the binary via the environment,
never argv, so it cannot leak into process listings.
|`from` |— |`From:` header value.
|`to` |— |Recipients, separated by commas and/or whitespace.
|`subject` |— |`Subject:` header value. ASCII is sent unchanged; anything
else goes out as RFC 2047 UTF-8 encoded-words, folded so no word exceeds 75
characters. CR/LF, or non-ASCII that is not valid UTF-8, fails the step.
|`content_language` |— |Optional `Content-Language` (RFC 3282): one or more
RFC 5646 tags, comma-separated — `en-GB`, or `en, cy` for a bilingual
message. Shape-checked (subtags of 1–8 ASCII letters or digits, the first
alphabetic) — looser than full RFC 5646 well-formedness, and not checked
against the IANA registry. A value that fails fails the step rather than
being repaired; one that passes is sent trimmed and `, `-joined.
|`body` |— |Plain text only, by design: no HTML, no remote images, no
tracking pixels. Dot-stuffed on the wire per RFC 5321 §4.5.2.
|`diagnose` |`false` |`true` = non-delivery probe reporting DNS, TCP, TLS,
EHLO and AUTH as separate stages. Nothing is authenticated or sent. See
<<diagnose>>.
|`handshake_only` |`false` |`true` = connect, TLS handshake, `EHLO`, `QUIT` —
no auth, nothing sent. For canary/CI verification against a real server.
|`timeout_seconds` |`60` |Whole-run deadline. A watchdog bounds connection,
handshake and every read and write, and fails the step with a diagnostic if it
is exceeded. Deliberately whole-run rather than per-operation; see
link:BUSTFILE.adoc[`BUSTFILE.adoc`].
|===

== Security properties

* **The pinned action ref fully determines the binary.** `action.yml` carries
  the SHA-256 of each release asset; the composite step downloads, verifies,
  then executes. A tampered asset fails the checksum, not the mail.
* **Byte-reproducible binaries.** Stripped static musl builds with Zig 0.16.0
  reproduce bit-identically from source regardless of build path. The release
  workflow rebuilds from the tagged source and refuses to publish unless its
  hashes equal the pins in `action.yml`.
* **The credential never touches argv.** All configuration reaches the binary
  as environment variables.
* **Header injection is rejected, never sanitized.** CR or LF anywhere in
  `from`, `to`, `subject` or `content_language` aborts the run before any byte
  reaches the wire. The rejection predicate is part of the Idris2
  specification. For `content_language` the acceptance predicate is stated as
  the tag grammar *and* that rejection check, and the theorem
  `contentLanguageNoInjection` pins the conjunction — dropping the injection
  check breaks the proof, not merely a test.
* **Proven protocol core.** The RFC 5321 client session — which commands may
  follow which replies, how reply codes classify, when `DATA` content must be
  dot-stuffed — is an Idris2 specification with machine-checked proofs.
  A generator emits the Zig state table *and* spec-evaluated golden test
  vectors; a CI gate regenerates both and fails on any drift. The gate carries
  a self-test proving it can fail.

== TLS implementation note (read this)

The binary uses Zig 0.16.0's standard-library TLS client — **vendored at
`src/tls/Client.zig` with one disclosed patch**. Upstream Zig cannot yet
answer a TLS 1.3 `CertificateRequest`
(https://github.com/ziglang/zig/issues/19521[ziglang/zig#19521]), and
Google-hosted SMTP endpoints such as `smtp.gmail.com:465` send one. The patch
accepts the request and declines it with an empty `Certificate` message per
RFC 8446 §4.4.2 — the correct behavior for a client with no certificate. It
is ~60 lines on an otherwise verbatim copy of the std file, every changed
region is marked `PATCH(#19521)`, and the file will be deleted in favor of
`std.crypto.tls.Client` once upstream handles the message. Certificate
verification against the system CA bundle is on and cannot be disabled.

== How it is built

[source]
----
spec/                Idris2: proven protocol specification (source of truth)
  Smtp/StateMachine.idr    session FSM + 5 protocol proofs
  Smtp/Serialize.idr       dot-stuffing, header rejection, Content-Language
                           grammar; stuffing + no-injection theorems
  Smtp/EmitZig.idr         emits the Zig table + golden vectors
src/
  generated/smtp_fsm.zig   GENERATED — never edit; CI diffs it against spec
  smtp.zig                 session driver walking the generated table
  message.zig              RFC 5322 date, stuffing, injection predicate
  tls/Client.zig           vendored std TLS client + #19521 patch (see above)
  main.zig                 env → config → connect → TLS → session
----

Build and test locally (Zig 0.16.0, Idris2 0.7.0):

[source,sh]
----
zig build test                                        # unit + golden vectors
zig build -Doptimize=ReleaseSafe -Dtarget=x86_64-linux-musl
scripts/check-fsm-drift.sh --selftest                 # spec ↔ generated diff
SMTP_HANDSHAKE_ONLY=true SMTP_SECURE=true \
SMTP_ADDR=smtp.gmail.com SMTP_PORT=465 ./zig-out/bin/smtp-notify
----

== Accessibility

Messages are plain text, deliberately and permanently: no HTML, no remote
images, no tracking pixel. That is an accessibility property, not a missing
feature — the message reads the same in a screen reader, a terminal mail
client and a braille display, and there is no layout to fail.

Two inputs support it:

* `content_language` tells assistive technology which language the message is
  in, so a screen reader picks the right voice and pronunciation rules. Use a
  list for bilingual messages (`en, cy`).
* Non-ASCII subjects are encoded per RFC 2047, so a subject in Welsh, Polish
  or Chinese arrives as written instead of as mojibake.

Diagnostic output is one line per stage, status word after the stage name,
so the answer is the first status that is not `ok` — no table to navigate, no
colour to see.

== Self-diagnosis

`diagnose: true` probes the server without delivering anything and reports
each stage on its own line (server text is folded onto that line, never
allowed to start one):

[source]
----
smtp-notify: diagnose: probing smtp.example.org:587 (starttls); no credential and no mail will be sent
smtp-notify: diagnose: DNS  ok          smtp.example.org -> 192.0.2.10:587
smtp-notify: diagnose: TCP  ok          connected to port 587
smtp-notify: diagnose: TLS  ok          STARTTLS upgrade, certificate verified for smtp.example.org
smtp-notify: diagnose: EHLO ok          server answered EHLO (after the upgrade)
smtp-notify: diagnose:      capabilities: STARTTLS=no 8BITMIME=yes SIZE=35882577 AUTH=[LOGIN XOAUTH2]
smtp-notify: diagnose: AUTH ok          this client would use LOGIN (credentials not sent, not verified)
smtp-notify: diagnose: MSG  ok          from/to/subject/content_language would be accepted
smtp-notify: diagnose: all stages ok; nothing was authenticated or sent
----

A failure names its stage and marks the rest `not-reached`, then exits 1:

[source]
----
smtp-notify: diagnose: TLS  FAIL        server did not advertise STARTTLS (advertised: STARTTLS=no, AUTH=[PLAIN LOGIN])
smtp-notify: diagnose: AUTH not-reached
smtp-notify: diagnose: MSG  not-reached
smtp-notify: diagnose: FAILED at TLS; nothing was authenticated or sent
----

What each stage establishes, and no more:

[cols="1,4"]
|===
|`DNS` |The name resolved, and to what.
|`TCP` |A connection to the port was accepted.
|`TLS` |A verified handshake — implicit, or the STARTTLS upgrade. `skipped`
under `secure: plaintext`.
|`EHLO` |The server greeted and answered EHLO (on STARTTLS, the post-upgrade
EHLO); its advertised capabilities are printed.
|`AUTH` |Which mechanism this client *would* use, chosen from the
post-TLS advertisement. No credential is sent, so this cannot tell a right
password from a wrong one — it tells "this client can speak this server's
AUTH" from "it cannot" (e.g. a server offering only `XOAUTH2`).
|`MSG` |Whether `from`, `to`, `subject` and `content_language`, if set, would
pass the checks a real send runs before connecting. Checked first, reported
last, so a local refusal never hides the server's answer. `skipped` when none
is set.
|===

A whole-run timeout is reported against the stage in flight, with the usual
cause for that stage and transport: a TLS stall under `secure: true` suggests
an implicit-TLS client aimed at a STARTTLS port; a greeting that never comes
under `secure: starttls` suggests a cleartext client aimed at 465.

`handshake_only: true` remains for canaries that want reachability and TLS
without the stage report.

== Performance

Measured 2026-09-30, one full delivery per run (greeting through `QUIT`) to the
same local sink, 100 runs each after three warm-ups:

[cols="2,1,1,1",options="header"]
|===
|Program |Wall, median |Wall, p95 |Peak RSS, median
|smtp-notify (static musl, 0.98 MB) |6.6 ms |8.7 ms |1.4 MiB
|dawidd6/action-send-mail v22, Node 24 |268.8 ms |319.2 ms |81.2 MiB
|===

About 40× faster to a delivered message and about 60× less memory. The method,
the host, the exact versions and the caveats — chiefly that this was a 2-vCPU
Linux VM, not a GitHub-hosted runner, and that neither action's download is
included — are in
link:docs/benchmarks/2026-09-30.adoc[`docs/benchmarks/2026-09-30.adoc`].
Reproduce with `scripts/benchmark.sh`, or on a real runner with the manually
dispatched `Benchmark` workflow, which writes the same table to the run
summary.

== Versioning

Pin by commit SHA (the estate's actions allowlist requires it). Tags `vX.Y.Z`
mark the commits whose `action.yml` pins match the release assets of the same
version. The asset URL inside `action.yml` names its own tag, so an action ref
always downloads the binary generation it was reviewed with.
